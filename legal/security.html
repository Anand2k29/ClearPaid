Security & data

What we do today, and what a production release would need.

What is in place today

  • Secrets stay on the server. PayPal and AI keys are read from environment variables and sent only in request headers. They are never sent to the browser, never put in URLs, and the health check returns provider names only.
  • Input limits. Request bodies are capped at 64 KB. Invoice fields and client messages are length-checked and validated before any provider is called.
  • Internal files are not served. The server does not serve the source, tests, process notes or environment files.
  • Documents stay on the device. Bill and document reading runs in the browser. Files are capped at 10 MB.
  • Injection resistance. Client text is treated as data. Instruction-like text is flagged and kept away from the model. Model output is validated against a fixed list of labels.
  • No money moves from our side. “Paid” is only accepted after PayPal confirms it.
  • Automated tests cover the server, the AI fallback, and the calculations.

Known limits

  • The prototype has no user accounts or login. Anyone who can open the app on a shared computer can see saved invoices.
  • Pages load fonts and libraries from public CDNs, which see visitors’ IP addresses.
  • Rate limits on free AI tiers can cause fallbacks to rule-based replies.
  • No security audit has been carried out.

Before any real use

  • Add user authentication and encrypted storage for invoice data.
  • Add HTTPS, a content security policy with pinned script hashes, and rate limiting on the API.
  • Commission an independent security review and a penetration test.
  • Confirm PCI DSS scope and payment-provider obligations with PayPal and your legal adviser.
  • Set data-retention periods and a deletion process.
